# 快慢系统协同的设计（2026-11-22）

> 回答「高效的快慢协同是如何设计的」。
> 本文讲**机制与取舍**，不是功能清单；功能清单见 dual-system.md。

---

## 0. 一句话设计

> **快系统持有"事实"与"手法"，慢系统持有"意图"与"取舍"；
> 两者之间只传「异常 + 上下文」和「意图 + 约束」，不传重复的数据、不传对方的活。**

一切设计都从这句话推导。

---

## 1. 切分依据：**决策的时间尺度**（不是"谁更聪明"）

判据只有一条：

> **「这个决策，换个存档 / 换个局面还成立吗？」**
> 成立 → 慢系统（分钟级、跨局泛化）
> 不成立 → 快系统（秒级、当前局面最优）

| 决策 | 时间尺度 | 归属 | 例子 |
|---|---|---|---|
| 这一轮下什么单 | ~10s | 快 | 在 (127,197) 铺梯子、挖氧石 |
| 选哪个材料 | ~10s | 快 | 砂岩够用就别用火成岩 |
| 这一轮先挖哪一列 | ~10s | 快 | 沿锁定列推进，不换列 |
| **这一局的主线是什么** | 分钟 | 慢 | 先打通地表换气，还是先产氧 |
| **放弃什么 / 冒什么险** | 分钟 | 慢 | 不往下挖（地下 CO2/水袋） |
| **失败几次就换方案** | 分钟 | 慢 | 连续 2 次找不到落点 → 升级 |
| **规则本身该怎么改** | 跨局 | 慢 | 「CO2 主导格不可当落脚点」写进代码 |

★ 慢系统的价值不在"更快更准"，而在**它能做快系统结构上做不到的判断**：
跨局泛化、语义权衡、非常规动作（亲自下精确工单）、修改快系统自己。

---

## 2. 信息流：**单向 + 零重复采集**

### 2.1 成本账（实测）

| 动作 | MCP 调用 | 延迟 |
|---|---|---|
| 快系统一轮（sense 并行采 5 个源） | ~5（并行） | **256 ms** |
| 快系统一轮总耗时 | — | **11~12 s**（10s 间隔 + 采集） |
| 快系统 → 慢系统 升级（写 escalation） | **0**（纯文件） | <1 ms |
| 慢系统看局势（audit / observe --cached） | **0**（读守护进程的 live_snapshot.json） | ~1 ms |
| 慢系统做一次完整决策 | 3~6（scout / probe / graph） | 秒级 |
| 慢系统 → 快系统 交底（改 plan.json） | 0（文件） | <1 ms |

### 2.2 三条设计规则

1. **唯一采集者**：只有快系统（守护进程）采集世界，慢系统**读它的落盘快照**。
   => 慢系统零 MCP；且**两边看到的永远是同一份真值**（不会一个看旧数据一个看新数据）。
2. **升级只传异常，不传数据**：escalation 里带的是 kind/node/detail/suggestion
   + 一份**上下文快照**（cycle/人口/氧气/食物），不是全局面。
   慢系统要细节时自己按需查（scout / probe / graph）——**按需付费**。
3. **交底只传意图，不传做法**：plan.json 里是目标序列 + 判据 + 语义目标，
   **不写死坐标**。怎么落地（选哪格、铺几块砖）是快系统的事。

★ 反面教材（本项目踩过）：
慢系统自己再采一次数据 → 双倍 MCP + 两份可能矛盾的真相；
plan 里写死坐标 → 换个存档全废（跨局污染的根源）。

---

## 3. 升级门槛：**只升级"确定性卡住"**

快系统每轮可能遇到各种不顺。如果全部升级，慢系统会被淹没（注意力是最稀缺资源）。

判据：**这个卡住，再试一次会不会好？**

| 会好 → 快系统自己扛 | 不会好 → 升级给慢系统 |
|---|---|
| 有人睡觉（暂时没活） | 预检不过（找不到落点/支撑） |
| 工单刚下，等复制人消化 | 语义目标无解（不知道往哪挖） |
| 材料暂时不够，自举能找到 | 材料缺且自举也找不到 |
| 研究锁（等条件变化） | 死工单（标记在位但没人能做） |
| | 依赖图死锁 / 人口下降 / 长期零进展 |

实现：stuck.rs 的 10 类**全是确定性卡住**（不是"暂时失败"）。

---

## 4. 批量语义：**一次慢系统介入处理一批问题**

pending 是**列表**不是单条：
- 慢系统一次读完所有问题 → **一次**决策 → **一次** ack；
- 避免"一个问题一次往返"把慢系统变成请求队列。

去重：raise() 按 (kind, node) 覆盖 => 持续性问题不会刷屏堆积。

---

## 5. 失败模式：**慢系统必须在场，也必须能不在场**

| 慢系统状态 | 快系统行为 |
|---|---|
| 在线且空闲 | 正常自主运行 |
| 在线且在处理 | 世界冻结（除 downed）→ 处理完 ack → 自动解冻 + 开窗 |
| **离线/崩溃** | 看门狗 300s → **降级解冻** → 继续自主运行（问题仍留在清单里等人看） |
| 从未接入 | planner 兜底：地形特征 → 策略族 → 依赖图，自己开局 |

★ 不变量：**慢系统不在快系统的关键路径上**。
慢系统的介入是**优化**，不是**依赖**。这与"AI 每轮指挥"是本质区别。

★ 为什么必须有看门狗：慢系统一离线，世界永远冻着 → 殖民地慢慢饿死 →
**这比全灭更糟**（全灭至少是明确的失败）。

---

## 6. 冻结边界（详见 dual-system.md §9）

核心不变量：**暂停 ≠ 停工**。
ONI 暂停会冻结倒计时 => 暂停期间人不耗氧、不受毒气伤害 => 冻结比停工安全得多。
**唯一例外是 downed**（暂停会阻断救援）→ 紧急态占空比（冻 20s → 跑 120s）。

---

## 7. 时序：一个周期内发生什么

    t0   快系统：sense(256ms) → judge(危险) → stuck::detect(卡住?)
    t0   ├─ 无卡住 → decide → execute → 下一轮
    t0   └─ 有卡住 → 冻结世界 + 写 escalation(0 MCP) + 停手
    ...  世界静止（安全），慢系统从容分析
    t1   慢系统：读 live_snapshot(0 MCP) + escalations + commands
                    → scout / probe / graph（按需）
                    → 改 plan.json(0 MCP) / 下精确工单 / 改代码
                    → ack（一次，处理全部）
    t2   快系统下一轮：pending 空 → 解除冻结 → 开窗 → 继续

## 8. 可量化的健康指标

想判断这套协同是否健康，看这四个数：

| 指标 | 健康区间 | 含义 |
|---|---|---|
| **升级频率** | 每 10~30 分钟一次 | 太频繁 = 快系统被淹没；太少 = 快系统在硬扛 |
| **升级/解决比** | > 3:1 | 每次介入要解决多个问题 |
| **慢系统介入成本** | < 5 次 MCP | 读缓存 + 按需查证，不做全量采集 |
| **看门狗触发次数** | 0 | 触发说明慢系统掉线了 |

## 9. 这套设计的三个已知弱点

1. **快系统的长竖井能力不足**：梯子链只铺 1 格就换列 → 需要慢系统亲自下工单。
   （正确的长期解法是让快系统沿锁定列连续铺，但这会显著增加单轮工作量，要权衡。）
2. **慢系统的复盘节奏未定**：现在是"有问题才介入"，缺一个"每 N 周期主动巡检"的节律。
3. **升级只有单向确认**：慢系统 ack 后快系统自动继续，但**没有回传给慢系统"问题真的解决了吗"**
   的确认回路（stuck::detect 下一轮自然会发现，但如果改好了就不会再报 —— 缺一个正反馈）。

## 10. 协同总线：为什么**不引入 DDS**，但借鉴了它的三个设计（2026-11-22）

用户提问：「快慢系统是否需要设计一套协同系统，比如 DDS 类似的中间件进行参与」。

### 10.1 判断：**不需要引入 DDS 这类重型中间件**

| DDS 的核心价值 | 我们的场景需要吗 |
|---|---|
| 多节点/多进程的**实时数据分发** | ❌ 单游戏 + 单快进程 + 一个慢系统，没有多节点分发 |
| **QoS**（优先级/时限/可靠性策略） | ✅ 需要 → 但只要**问题语义**的那部分 |
| **服务发现**（自动找谁提供什么） | ❌ 双方固定（快=守护进程，慢=主 agent） |
| 实时传输层（RTPS）+ QoS 协商 | ❌ 事件量一局几十条，文件完全够 |

**三条否决理由**：
1. **DDS 的核心能力用不上**（没有多节点分发问题）；
2. **多一个常驻进程 = 多一个故障点** —— 而我们恰恰刚被"慢系统离线"吃过亏
   （没有看门狗 → 殖民地饿死）。**架构上要减少故障点，不是增加**；
3. **复杂度不匹配**：为一个单进程对局引入 DDS 的配置/运维成本，得不偿失。

### 10.2 但要借鉴它的三个设计 → 轻量协同总线（`bus.rs`）

| DDS 概念 | 我们的轻量实现 | 为什么需要 |
|---|---|---|
| **发布/订阅** | 双方都只 publish/subscribe 事件，**互不直接调用** | 解耦：快系统不"知道"慢系统是谁，慢系统也不"知道"快系统怎么执行 |
| **QoS** | ① 优先级（Critical/Warn/Info）② **时效 TTL**（过期自动失效）③ **去重**（同 kind+node 折叠）④ **批量窗口**（慢系统一次读到的是"当前仍成立的问题集合"） | 防止慢系统被历史噪声淹没 |
| **可回放日志** | append-only `events.jsonl` → `replay(since)` | **慢系统复盘**（"这一局问题是怎么出现、升级、被处理的"） |

### 10.3 事件的生命周期闭环（修「只有单向确认」的弱点）

    publish(Open)  ──慢系统接手──►  acknowledge(Acknowledged)  ──确认解决──►  resolve(Resolved)
         ▲                                                                        │
         └──────────────── 下一轮 stuck::detect 没再命中 = 自动闭环 ◄─────────────┘

★ 以前只有"升级 → ack"单向；现在有 **resolve**，且"下一轮没再命中"本身就是一种隐式 resolve。

### 10.4 统一时间线

三类协同事件（卡住/升级、用户指令、计划变更）都进同一条 `events.jsonl`：

    oni bus               待处理（QoS 过滤后）
    oni bus timeline      全部（可回放）
    oni bus ack <id>      确认接手
    oni bus resolve <id>  确认解决

★ 慢系统不再需要在三个地方（escalations / commands / audit）分别看，
   **一个时间线看完所有协同事件**。

## 11. 本轮修复的三个弱点

| 弱点 | 根因 | 修法 |
|---|---|---|
| **快系统长竖井不行**（梯子链只铺 1 格就换列） | ★★ `grid::walkable_with()` 里梯子的特判写在 `if !open { return false; }` **之后**，而 match 里没有 `Kind::Ladder` → **梯子格永远 open=false → 梯子被当成墙**（从项目第一天就存在的致命 bug） | 梯子直接进 open 集合；`climbable` 的种子从稀疏官方样本换成**网格 BFS 可达集**（梯子链的根部才正确） |
| **慢系统复盘节奏未定** | 没有统一事件流 | 协同总线的 `replay(since)`：慢系统可按周期回放整局事件流 |
| **升级只有单向确认** | ack 后没有"问题真解决了吗"的回路 | 事件生命周期 Open → Acknowledged → **Resolved**（+`resolve` 命令） |

★ 另修两个实战误报：
* **去抖**：同一 kind 连续命中 **2 轮**才升级（瞬时状态不升级、不冻结）。
* **常态差事不当危险**：「在 CO₂ 格子里」是 ONI 常态（睡觉/擦洗/找安全区/恢复呼吸）
  → 排除这些差事 + 阈值从 95 收紧到 60。
