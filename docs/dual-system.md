# 快慢双系统架构（2026-11-22 定稿）

> 用户定调：**AI 要不断参与规划、处理问题；AI 是慢系统，代理是快系统。**
> 本文是这一分工的落地规范。

---

## 1. 为什么必须是双系统

《缺氧》的对局是一个**开放世界 + 长时程 + 不可逆死亡**的问题：

* **快问题**（每 10 秒都要答）：现在最危险的是什么？这一轮该下什么单？
  → 必须由程序做（人不可能每 10 秒介入）。
* **慢问题**（每几分钟/每个关键节点）：这一局的战略是什么？目标是哪个？
  遇到"规则解不开"怎么办？上一局的教训能不能泛化？
  → 必须由 **AI** 做（需要理解语义、权衡、跨局泛化）。

**把两者混在一起的两种失败（都真实发生过）**：

| 错误 | 症状 | 本局案例 |
|---|---|---|
| **只有快系统**（AI 退场） | 规则解不开时无限重试/空转；没人做大判断 | 本轮初版：planner 接管规划后，"找不到厕所落点"只会暂缓重试 |
| **只有慢系统**（AI 每轮指挥） | 回合太慢、烧周期；细节做不了 | 上一局：我手工逐格下梯子，代理全程空转 |

---

## 2. 分工表

| | 慢系统（AI / 主 agent） | 快系统（代理 / 守护进程） |
|---|---|---|
| **节奏** | 几秒~几分钟一次；开局一次、每次 escalation 一次 | 每 10 秒一轮 |
| **视野** | 全局：态势卡 + scout + 全图 + 跨局经验 | 局部：当前局面快照 + 本轮目标 |
| **产物** | plan.json（战略层）、代码、AGENTS.md 规则、records/* | 工单（挖/建/梯/砖/接线/收割）、选点、材料选择 |
| **决策权** | 目标顺序、换不换主线、什么时候放弃当前方案 | 怎么落地这一轮（选哪格、选什么材料、局部降级） |
| **遇到卡点** | —— | **escalation：喊人 + 停手** |
| **不许做** | 替代理做每轮执行 | 自己做跨周期战略判断 |

**不变式**：*慢系统不替快系统干活，快系统不替慢系统做决定。*

## 3. 交接协议（本轮新落地）

### 3.1 快 → 慢：escalation（喊人）

触发条件（**都是"规则解不开"**的情况，不是"再试一次能好"）：

| Kind | 触发 | 例子 |
|---|---|---|
| NodeFailing | 保命节点连续失败 | 产氧节点连撞 N 次（材料/空间解不了） |
| StrategyMismatch | 连续找不到建造落点 | 1 格高走廊放不下 2×3 厕所 → 布局决策 |
| NoFeasibleTarget | 语义目标找不到任何可行解 | 自举找不到任何可挖材料 |
| Deadlock | 依赖图没有可执行节点 | requires 指向不存在的节点 |
| NoProgress | 连续多轮零进展 | — |
| UnknownHazard | 未识别的危险模式 | 多人同时倒地 |

**铁律：喊人之后不许继续瞎试。**
旧行为是"保命节点失败就重置计数 → 下一轮再试" → 无限循环、白烧周期。
新行为：升级上报 + **停手**（世界冻回暂停，等慢系统改计划）。

产物：
* ~/.oni-agent/saves/<指纹>/escalations/pending.json（待处理，按存档隔离）
* ~/.oni-agent/saves/<指纹>/escalations/history.jsonl（历史）
* 代理日志里一行 🆘 显眼标记。

### 3.2 慢 → 快：改计划

慢系统处理完，用 `oni escalations ack <id>` 告诉快系统"我处理了，继续"。
同时把新战略写回 plan.json（走 saveswitch::write_plan，指纹永远正确）。

### 3.3 慢系统的工具箱

| 命令 | 用途 |
|---|---|
| oni observe | 全局态势卡（人/气/资源/建筑/电力/趋势） |
| oni scout | 资源分布侦察（距离 + **在下方还是上方**） |
| oni graph --full | 气室图 + 到地表路径（几何最短路 + 未探索标记） |
| oni plan-auto [--keep] | **自动规划器**：地形特征 → 策略族 → 依赖图（AI 的草稿生成器 + AI 不在线时的兜底） |
| oni escalations | **快系统喊上来的请求**（慢系统工作台） |
| oni note / oni promote | 局内笔记 / 上提到通用记忆 |
| oni state | 存档身份与局内缓存目录（跨局隔离检查） |

## 4. 自动规划器的定位（重要修正）

planner.rs **不是**用来取代 AI 的，而是两样东西：

1. **AI 的草稿生成器**：AI 说"这一局大概怎么打"，planner 按地形特征生成一个**合规初稿**
   （零硬编码坐标、有判据、有依赖），AI 再审阅/改写/删减。
2. **AI 不在线时的兜底**：没有 AI 时，代理仍能自己开局（保底不至于全灭）。

**AI 保留的权力**：目标顺序、换不换主线、放弃什么、风险取舍。
planner 的 6 个策略族只是"常见开局的先验"，不是硬规则。

## 7. 四条通道（完整闭环，2026-11-22 补全）

    ┌─────────────┐   指令    ┌──────────────┐  plan.json  ┌──────────────┐
    │   用户      │ ────────► │  慢系统(AI)  │ ──────────► │ 快系统(代理) │
    │ (可随时下达) │ ◄──────── │  巡检/决策    │ ◄───────── │  感知/执行   │
    └─────────────┘   回执    └──────┬───────┘  工单      └──────┬───────┘
                                       ▲                          │
                                       │  escalations（喊人）      │
                                       └──────────────────────────┘
                     audit（主动巡检发现的问题）也进慢系统

| # | 通道 | 载体 | 谁发起 | 谁消费 |
|---|---|---|---|---|
| 1 | 用户 → 慢系统 | oni command add "<指令>" 队列（按存档隔离） | 用户 | 慢系统翻译成计划/工单/代码 |
| 2 | 慢系统 → 快系统 | plan.json（战略层）+ 直接下精确工单 | 慢系统 | 快系统执行 |
| 3 | 快系统 → 慢系统 | escalations/pending.json（喊人 + 停手） | 快系统 | 慢系统决策 → ack |
| 4 | 慢系统 → 慢系统 | oni audit（**主动巡检**） | 慢系统 | 慢系统（不等故障） |

### 7.1 通道 1：用户指令（本轮新增）

    oni command add "优先建 3 个厕所，全部建在富氧区；别再往下挖了"
    # 慢系统读到后：
    #   ① 翻译成计划修改（A2 提到最前、判据 toilets>=3、落点写死）
    #   ② 翻译成代码修改（「别再往下挖」→ 自举时下方材料直接排除）
    #   ③ 回执
    oni command done <id> "已落实：① … ② … ③ …"

★ **指令要落到「计划 + 代码」两处**：只改计划会被代理的局部逻辑绕开；
只改代码则没有全局意图。"别再往下挖"这种**硬约束**必须进代码。

### 7.2 通道 4：主动巡检（本轮新增）

`oni audit` 跑一遍体检清单，输出问题 + 建议：

| 检查码 | 触发 | 建议动作 |
|---|---|---|
| pop.drop | 人口下降 | 查死因 + 回滚存档 |
| hygiene.no_toilet | 膀胱>80% 且厕所<人口 | 优先建厕所（富氧区+地板砖） |
| sleep.no_bed | 床位<人口 | 建床 |
| air.co2_ratio | O₂/(O₂+CO₂) < 75% | 通地表/拓宽通风；居住区上移 |
| oxygen.stalled | 有产氧件但空气比仍低 | 查三件套：投料/接线/位置 |
| power.not_connected | 有发电机但 consumerUsedWatts=0 | 接线到耗电建筑 |
| food.runway | 食物 < 3 周期 | 收割应急 + 建农场 |
| hygiene.polluted_air | 污染氧 > 40kg | 区域擦洗 + 居住区搬离 |

★ 与 escalation 的区别：**audit 是慢系统主动跑（无故障也能发现问题），
escalate 是快系统被动喊（遇到解不开的情况）**。两者产出统一交给慢系统决策。

## 9. 冻结边界（严谨版，2026-11-22 用户追问后重做）

> 用户原话：「慢系统执行的时候，需要暂停，包括慢系统接手到用户下发的指令，
> 这些暂停的边界，你都处理好了吗」

### 9.1 完整规则表

| # | 触发情形 | 世界状态 | 标志 | 解除条件 | 理由 |
|---|---|---|---|---|---|
| 1 | 用户手动暂停 | ⏸ 暂停 | `user_paused` | **只有用户**（代理绝不越权恢复） | 用户主权 |
| 2 | `oni hold`（主 agent 改代码） | ⏸ 暂停 | — | `oni release` | 改代码期世界不该动 |
| 3 | **用户下发指令**（`oni command add`） | ⏸ **立即暂停** | `escalation_hold` | 慢系统 ack（或看门狗） | 指令翻译要时间，期间别做错事 |
| 4 | **快系统卡住**（统一检测命中） | ▶ **继续跑**（只停工不下新单） | `escalation_hold` | 慢系统 ack（或看门狗） | ★ 2026-11-22 修正：冻结世界 → 用户暂停误判 → 无人恢复 → 膀胱爆（全灭）；停工期世界继续跑，已有工单照做 |
| 5 | **有人倒地**（downed） | ⏸▶ **占空比**（冻20s→跑120s） | — | 环境改善后自动 | ⚠️ **暂停会阻断救援**：倒地的只能靠环境改善恢复，而环境改善需要游戏在跑 |
| 6 | 人口为 0 | ⏸ 暂停 | — | 人工回滚存档 | 没人可救，占空比只是白烧周期 |
| 7 | 施工窗口正常到期 | ⏸ 暂停 + 20s 后自持续窗 | `frozen` | 自动 | 无人值守时别停摆 |
| 8 | 空跑停机 | ⏸ 暂停 | `idle_stopped` | 人工 | "停→恢复→再停"会空转烧周期 |
| 9 | **等慢系统超时**（>300s 无人处理） | ▶ **降级解除冻结** | 清除 | 自动 | ⚠️ 慢系统可能离线/崩溃 → **不能让殖民地永远冻死** |

★ **三条不变量**：
1. **暂停 ≠ 停工**。ONI 的暂停会冻结倒计时 → 暂停期间人不耗氧、不被毒气伤害 →
   所以"冻结"比"停工"安全得多（唯一例外是 downed，见第 5 条）。
2. **只有 downed 例外**。其余任何"需要慢系统"的场合，冻结世界都是安全且必要的。
3. **看门狗兜底**。没有看门狗，慢系统一离线，殖民地就慢慢饿死 —— 这是**比全灭更糟的失败模式**
   （全灭至少是明确的）。

### 9.2.1 ★★ 暂停所有权（2026-11-22 死锁根治）

四种内存标志（user_paused / frozen / idle_stopped / paused_by_us）**靠排除法推断
"是谁暂停的"，进程一重启就全清零 → 误判"用户暂停" → 谁都不恢复 → 死锁。
正解：`crates/oni-engine/src/control.rs` 把 **owner + reason + since** 落盘到
`saves/<fp>/control.json`（用 `last_seen()` 拼路径，CLI 与守护进程两边一致）。

| owner | 谁能恢复 | 场景 |
|---|---|---|
| `user` | 只有用户 | hook / `oni pause` —— 代理绝不越权 |
| `agent` | 代理 | 窗口到期 / 空闲停机 / 卡住停工 |
| `hold` | 只有 `oni release` | 主 agent 改代码 |
| `escalation` | ack / 看门狗 | 等慢系统 |
| `none` | —— | 世界在跑 |

★ `oni window <秒>` 是"用户授权代理恢复"的信号：清掉 owner → 代理开工。
★ 未知来源的暂停保守判 `user`（宁可不恢复，也不越权）。
★ 效果回执：每次暂停/恢复写 bus 事件；Urgent 匹配不到节点升级为 escalation（不再只写日志）。

### 9.2 四种暂停标志互不串味

| 标志 | 含义 | 谁能解除 |
|---|---|---|
| `user_paused` | 用户手动暂停 | 只有用户 |
| `frozen` | 窗口正常到期（可自持） | 自动（20s 后续窗） |
| `idle_stopped` | 空跑停机 | 人工（防空转） |
| `escalation_hold` | **等慢系统** | 慢系统 ack 或看门狗 |

## 10. 「代理卡住」到底涉及哪些情况（单一真相来源）

> 全部收在 `crates/oni-engine/src/stuck.rs` 的 `detect()` 里 ——
> **每轮跑一遍，产出统一清单**；清单非空 → 冻结 + 升级。
> 之前这些判定散落在七八个 `if` 里 → **漏一个就是一个致命缺口**。

| # | 卡住类型 | 判据 | 后果（不处理会怎样） |
|---|---|---|---|
| 1 | **预检不过** | 找不到落点 / 支撑不实 / 落脚点不可达 / 占格被占 | 节点永远失败 → 空转烧周期 |
| 2 | **语义目标找不到** | surface / oxygen / element:X 都找不到可行解 | 代理不知道往哪走 → 反复报同一错 |
| 3 | **材料缺失** | 缺建材且自举也找不到可挖材料 | 每轮尝试注定失败的建造 |
| 4 | **死工单** | 地图上有 dig 标记，但无待办 + 全员空闲 | ⚠️ mod 的 dig 标记不进 pendingOrders → 代理误判"空闲"→ 冻回 → **工单永不执行** |
| 5 | **节点反复失败** | 动作连续失败 ≥ N 次 | 无限重试同一个方案 |
| 6 | **依赖图死锁** | 没有可执行节点（requires 指向不存在的节点 / 全被熔断） | 刷屏"依赖图里没有可执行目标" |
| 7 | **复制人倒地** | 差事 = 失去行动能力 | 不执行任何差事；**且搬不动**（move_to 要寻路） |
| 8 | **复制人在毒气格** | 所在格不可呼吸 且 呼吸 < 95 | 呼吸一路掉到 0 → 倒地 → 死 |
| 9 | **人口下降** | 本轮人数 < 上轮 | 有人没了（红线） |
| 10 | **长期零进展** | 连续 ≥ 3 轮指纹不变 | 方案本身走不通（该换，而不是加轮次） |

★ **第 4 条最隐蔽**：mod 的挖掘标记**不进** `pendingOrders`，所以"有工单在位"和"有活可干"
在官方数据里**无法区分**。只能用"地图标记数 > 0 且无待办且全员空闲"这个组合反推死工单。

★ **第 7 条的连带事实**（AGENTS.md 13.36 / 17）：倒地的复制人**搬不动** →
救援机制对"倒地"实际无效 → 必须在**事前**避免（居住区远离毒气 + 富氧区有床）。
